# Auth and Permissions

Constraint Management has two permissions, and access is decided by the HTTP
method:

| Requests | Permission |
| --- | --- |
| `GET`, `HEAD` | `constraints.review` |
| `POST`, `PUT`, `PATCH`, `DELETE` | `constraints.review.decide` |

`GET /health` is always public.

## Roles

| Role | Grants |
| --- | --- |
| `admin` | Everything, regardless of other permissions. |
| `auditor` | `constraints.review` only. Auditors are always refused on writes, even if they also hold `constraints.review.decide`. |

Roles and permissions can come from two places, and are merged when both are
present.

## Bearer tokens

```http
Authorization: Bearer <access token>
```

Tokens are verified against `ZITADEL_JWKS_URL`, `ZITADEL_ISSUER_URL`, and
`ZITADEL_AUDIENCE`. From the verified token:

- Roles are read from the claim named by `ZITADEL_GROUPS_CLAIM` (default
  `groups`). Only `admin` and `auditor` are recognized; other values are
  ignored.
- Permissions are read from the claim named by `ZITADEL_PERMISSIONS_CLAIM`
  (default `permissions`). Each value must be a known permission, or the
  request fails with `token_permission_unknown`.

## Trusted actor headers

A backend that already authenticated the user, such as the Constraint
Management dashboard's server, can forward the actor instead of a token:

| Header | Meaning |
| --- | --- |
| `x-actor-id` | Required. The actor's subject, recorded as `created_by`/`updated_by`. |
| `x-actor-roles` | Optional, comma-separated: `admin`, `auditor`. |
| `x-actor-permissions` | Optional, comma-separated permissions. |

```bash
curl "$CONSTRAINT_MANAGEMENT_API_BASE_URL/no-fly-zones" \
  -H "x-actor-id: 312244512312345678" \
  -H "x-actor-roles: auditor"
```

:::warning[Server-side only]

The API trusts these headers as sent. Only a backend you control should set
them, and that backend must strip any copies sent by browsers. Do not expose
the API publicly with actor headers enabled. Browsers cannot send them anyway:
CORS only allows `Authorization` and `Content-Type`.

:::

## Errors

| Status | `detail` | Cause |
| --- | --- | --- |
| `400` | `actor_id_required` | Role or permission headers without `x-actor-id`. |
| `400` | `actor_id_invalid` | `x-actor-id` is blank or repeated. |
| `400` | `actor_role_unknown` | Unknown role in `x-actor-roles`. |
| `400` | `actor_permission_unknown` | Unknown permission in `x-actor-permissions`. |
| `400` | `token_permission_unknown` | Unknown permission in the token's permissions claim. |
| `401` | `invalid_authorization_header` | The header is not `Bearer <token>`. |
| `401` | `invalid_token` | The token failed verification. |
| `403` | `permission_denied` | The caller lacks the permission for the method. |

## Audit actor

Writes store the actor subject in `created_by` and `updated_by`, and in the
audit log `actor`. Requests without an actor are recorded as `system`.
