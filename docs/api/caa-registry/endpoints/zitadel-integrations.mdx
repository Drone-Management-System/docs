# ZITADEL Integrations

These endpoints are ZITADEL Actions V2 targets. ZITADEL calls them when a human
user is added or removed, and the registry creates, updates, or soft-deletes
the matching user. They take no bearer token. Every call is verified with an
HMAC signature instead.

## Signature

ZITADEL signs each call with the target's signing key:

```text
ZITADEL-Signature: t=1767225600,v1=5f2b...e9
```

The API computes `HMAC-SHA256(signing_key, "<t>.<raw body>")` and compares it
with every `v1` value in constant time. The timestamp must be within
`ZITADEL_ACTION_SIGNATURE_TOLERANCE_SECONDS` (default 300) of the server
clock. `X-ZITADEL-Signature` is accepted as an alias.

Because the signature covers the raw bytes, the **Try it** console cannot
produce a valid call. Use ZITADEL's target test, or sign a body yourself:

```bash
BODY='{"aggregateID":"298183789123456789","event_type":"user.removed"}'
T=$(date +%s)
SIG=$(printf '%s.%s' "$T" "$BODY" | openssl dgst -sha256 -hmac "$SIGNING_KEY" -hex | cut -d' ' -f2)
curl -X POST "$CAA_REGISTRY_API_BASE_URL/integrations/zitadel/users" \
  -H "Content-Type: application/json" \
  -H "ZITADEL-Signature: t=$T,v1=$SIG" \
  --data-raw "$BODY"
```

## How users are matched

For `user.human.added`, the registry looks for an existing user by its
`zitadel` identity link, then by `zitadel_user_id`, then by email. A match is
updated; otherwise a user is created. Each sync also writes a
provider-neutral `user_identity` row (`provider: "zitadel"`), which is the link
new integrations should rely on.

`user.removed` never hard-deletes. It sets `zitadel_status` to `deleted`,
records `zitadel_deleted_at`, and marks the identity link deleted. A removal
for a user that was never synced returns `action: "missing"` with `200`, so
ZITADEL does not keep retrying.

| `action` | Status | Audit action |
| --- | --- | --- |
| `created` | `201` | `zitadel_sync_create` |
| `updated` | `200` | `zitadel_sync_update` |
| `unchanged` | `200` | none |
| `marked_deleted` | `200` | `zitadel_sync_delete` |
| `missing` | `200` | none |

## Operational notes

- Configure the target as a REST webhook with a JSON payload.
- **Interrupt on Error** blocks the ZITADEL user operation when this API is
  down. Test carefully before enabling it.
- Follow integration logs with:

```bash
sudo journalctl -u caa-registry.service -f -o cat | grep --line-buffered zitadel_user
```

- If events were missed, run a [reconciliation job](./system-jobs) to catch up.
