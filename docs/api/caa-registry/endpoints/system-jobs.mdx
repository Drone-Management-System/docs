# System Jobs

System jobs are durable background tasks stored in `system_jobs`. Today there
is one job type, `zitadel_user_reconciliation`, which pulls users from the
ZITADEL API to repair anything the [integration webhooks](./zitadel-integrations)
missed.

Jobs move through `queued`, then `running`, then `completed` or `failed`. The
in-process worker polls for queued jobs every
`SYSTEM_JOB_WORKER_POLL_INTERVAL_MS`. Jobs stuck in `running` longer than
`SYSTEM_JOB_STALE_RUNNING_MS` (2 hours by default) are recovered.

| Mode | What it reads | Cursor |
| --- | --- | --- |
| `events` | ZITADEL `user.human.added` and `user.removed` events since the stored cursor. | Advanced after a successful, non-dry run when `commitCursor` is on. |
| `full_scan` | Every human user, up to `ZITADEL_USER_SYNC_MAX_USERS`. | Not used. |

A job fails if any user fails to sync. The failures are listed in
`payload.failures`.

Job endpoints use the `users.read` and `users.write` permissions, and return
camelCase keys.
