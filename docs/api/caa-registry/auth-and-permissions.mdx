# Auth and Permissions

Every route requires a ZITADEL bearer token, with three exceptions:

| Route | Authentication |
| --- | --- |
| `GET /health` | Public while `ZITADEL_BYPASS_AUTH_FOR_HEALTH` is on (the default). |
| `POST /integrations/zitadel/users` | ZITADEL Actions signature instead of a token. |
| `POST /integrations/zitadel/users/deleted` | ZITADEL Actions signature instead of a token. |

The two integration routes are only token-free while the health bypass is on,
because they share the same public-path list.

## Sending a token

```http
Authorization: Bearer <access token>
```

For a service user, follow [Sign and Call APIs](../../development/sign-and-call-api)
to sign a JWT assertion and exchange it for an access token.

## Token verification

Tokens are verified with `jose` against the remote JWKS:

| Check | Configuration |
| --- | --- |
| Signature | `ZITADEL_JWKS_URL` |
| Issuer (`iss`) | `ZITADEL_ISSUER_URL` |
| Audience (`aud`) | `ZITADEL_AUDIENCE` |
| Subject (`sub`) | Must be present. |

| Status | `detail` | Cause |
| --- | --- | --- |
| `401` | `authentication_required` | No `Authorization` header. |
| `401` | `invalid_authorization_header` | The header is not `Bearer <token>`. |
| `401` | `invalid_token` | Signature, issuer, audience, or expiry check failed. |
| `401` | `token_subject_missing` | The token has no `sub`. |
| `403` | `permission_denied` | The token is valid but lacks the route's permission. |

The service logs the expected issuer and audience on `invalid_token`, and the
required permission plus the caller's groups on `permission_denied`.

## Where permissions come from

The service reads the claim named by `ZITADEL_GROUPS_CLAIM` (default
`groups`). That claim can be a string, an array of strings, or an object whose
keys are group names, which matches ZITADEL's project roles claim.

Each value is then resolved:

1. A known group name expands to its permission set (table below).
2. A value containing a dot, such as `ua.read`, is taken as a permission as-is.
3. `*` and `admin.all` grant everything.

Wildcards also work per resource or per action: `ua.*` grants every `ua`
permission, and `*.read` grants every read permission.

## Groups

| Group | Permissions |
| --- | --- |
| `caa_registry_admin` | All permissions (`*`). |
| `caa_registry_manager` | `organizations.read`, `organizations.write`, `users.read`, `users.write`, `operators.read`, `operators.write`, `remote_ids.read`, `remote_ids.write`, `ua.read`, `ua.write`, `reference.read` |
| `caa_registry_viewer` | `organizations.read`, `users.read`, `operators.read`, `remote_ids.read`, `ua.read`, `reference.read`, `search.read` |
| `caa_registry_auditor` | `audit.read` |

Managers can create and edit but not delete, and cannot read audit history or
use search. Combine groups when a user needs both.

## Permissions

| Permission | Grants |
| --- | --- |
| `organizations.read` / `.write` / `.delete` | Organizations, organization admins, organization property definitions and values. |
| `users.read` / `.write` / `.delete` | Registry users and national ids. `users.read` and `users.write` also cover [system jobs](./endpoints/system-jobs). |
| `operators.read` / `.write` / `.delete` | Operators, operator property definitions and values. |
| `ua.read` / `.write` / `.delete` | UA aircraft, UA lookup, UA property definitions and values. |
| `remote_ids.read` / `.write` / `.delete` | Remote ID records. |
| `reference.read` / `.write` / `.delete` | Operator types and user types. |
| `audit.read` | `/audit` and every `/:entity/:id/history` route. |
| `search.read` | `GET /search`. |

The `uas.*` permissions from earlier versions no longer exist.

## Audit actor

Every write records an actor in the audit log: the token's email, then its
username, then its subject. Writes made by the ZITADEL integration and system
jobs are recorded as `system`.
