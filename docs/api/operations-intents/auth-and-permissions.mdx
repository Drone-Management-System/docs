# Auth and Permissions

Callers identify themselves with a ZITADEL bearer token, trusted actor headers
from a backend, or both.

## When credentials are required

| Setting | Behavior |
| --- | --- |
| `AUTH_ENABLED=true` | Every route except `GET /health` needs a bearer token or actor headers. |
| `AUTH_ENABLED` unset or `false` | Credentials are optional. Requests without them run as an anonymous actor and are recorded as `system`. |
| `ZITADEL_BYPASS_AUTH_FOR_HEALTH` (default on) | `GET /health` is always public. |

Enable `AUTH_ENABLED` in every shared environment.

## Bearer tokens

```http
Authorization: Bearer <access token>
```

Tokens are verified against `ZITADEL_JWKS_URL`, `ZITADEL_ISSUER_URL`, and
`ZITADEL_AUDIENCE`. Groups are read from `ZITADEL_GROUPS_CLAIM` (default
`groups`).

## Trusted actor headers

The Operations Intents dashboard's server forwards the signed-in user as
headers, so the browser never needs a token for this API:

| Header | Meaning |
| --- | --- |
| `x-actor-id` | The user's ZITADEL subject. Required when the other actor headers are present. Recorded as the audit actor. |
| `x-actor-roles` | Optional, comma-separated: `operator`, `auditor`. |
| `x-actor-permissions` | Optional, comma-separated permission names, validated against the API's list. |

When a bearer token is also sent, it is verified, and its groups and
permissions are merged with the headers.

:::warning[Server-side only]

The API trusts actor headers as sent. Only a backend you control should set
them, and that backend must strip any copies sent by browsers. Browsers cannot
send them directly: CORS only allows `Authorization` and `Content-Type`.

:::

## Roles and permissions

Only the review workflow checks permissions. CRUD and package routes accept any
authenticated caller.

| Role | Permissions | Can |
| --- | --- | --- |
| `operator` | `operations.review` | Request approval. |
| `auditor` | `operations.review`, `operations.review.decide` | Request approval, approve, reject, request changes. |

ZITADEL groups are mapped to these roles by their last path segment:

| Group (or `.../group`) | Role |
| --- | --- |
| `operator`, `caa_registry_manager`, `caa_registry_operator` | `operator` |
| `auditor`, `admin`, `administrator`, `caa_registry_admin`, `caa_registry_auditor` | `auditor` |

`caa_registry_admin` also maps to `*`, so it passes every check. As in the CAA
Registry, a group containing a dot (for example `operations.review.decide`) is
taken as a permission directly.

| Route | Needs |
| --- | --- |
| `POST /operational-intents/:id/approval-requests` | `operations.review` or `operations.review.decide` |
| `POST .../approve`, `.../reject`, `.../request-changes` | `operations.review.decide` |
| `POST .../validate`, `GET .../review-status` | Any caller |

## Errors

| Status | `detail` | Cause |
| --- | --- | --- |
| `400` | `actor_id_header_required` | Actor role or permission headers without `x-actor-id`. |
| `400` | `actor_roles_header_invalid` | A role other than `operator` or `auditor`. |
| `400` | `actor_permissions_header_invalid` | An unknown permission name. |
| `401` | `authentication_required` | `AUTH_ENABLED=true` and no credentials. |
| `401` | `invalid_authorization_header` | The header is not `Bearer <token>`. |
| `401` | `invalid_token` | The token failed verification. |
| `403` | `APPROVAL_UNAUTHORIZED_REVIEWER` | A review decision without the required permission. |

Review routes use a different error handler. Authentication failures on those
routes currently come back as `500 INTERNAL_SERVER_ERROR` in the review
envelope, not as `401`.

## Audit actor

The audit actor is `x-actor-id` when present; otherwise the token's email,
username, or subject; otherwise `system`.
